# Витрина бронирований в DuckDB и ClickHouse

Одна строка `fact_booking` = одно бронирование, представленное отдельной записью
фиксированного исходного CSV. Модель описана в [passport.md](passport.md)
и [star.md](star.md): один факт и пять измерений.

## Запуск

Нужны Python 3.11+ и два исходника: `data/raw/H1.csv`, `data/raw/H2.csv`.
Из корня проекта:

```powershell
python -m pip install -r requirements.txt
python etl/load_duckdb.py
```

Результаты:

- `data/booking.duckdb` — локальная база с шестью таблицами;
- `data/checks_duckdb.txt` — последний отчёт, записанный Python-скриптом;
- `data/rejected_duckdb.csv` — отклонённые записи: файл, исходный номер записи,
  номер физической строки, причина и исходные значения в JSON;
- `etl/lab05_runs.txt` — сохранённый лог двух запусков и сверка итогов;
- `sql/ddl_duckdb.sql` — создание таблиц с первичными и внешними ключами;
- `sql/check_duckdb.sql` — проверочные запросы; выполняются загрузчиком,
  поскольку сверка с сырьём использует временную таблицу `raw_booking`.

## Загрузка и повторный запуск

`etl/load_duckdb.py` читает CSV стандартным модулем Python `csv`, обрезает
пробелы, распознаёт пустые строки и маркеры `NULL`, `NA`, `N/A` как пропуски
(в текущем сырье `NA` встречается в `Children`). Номер записи
данных начинается с 1 без заголовка. `booking_id` имеет вид `H1:1`, `H2:1`.
Совпадающие по содержимому записи не удаляются. Сырьё не изменяется.

Даты заезда собираются из года, названия месяца и дня.
Пропуски измерений ссылаются на явные значения `UNKNOWN`; неизвестная дата имеет
ключ 0. Календарь непрерывный от минимальной до максимальной даты заезда/статуса,
`day_of_week` — от 1 (понедельник) до 7 (воскресенье).
Пропуски `children` и `adr` сохраняются как SQL NULL. `adr` хранится как `DECIMAL(18,2)`.

Каждая запись проверяется до SQL-загрузки. Ошибки дат, чисел, обязательных
значений, статусов и количества CSV-колонок отклоняют только эту запись;
обработка следующих записей продолжается. Исходная нумерация сохраняется:
если запись `H1:2` отклонена, следующая имеет ключ `H1:3`.

## Просмотр схемы и запуск SQL

Скрипт `scripts/query_duckdb.py` использует установленный DuckDB, без pandas
и дополнительных зависимостей. Из корня проекта:

```powershell
# Без параметров — столбцы, типы и ограничения всех таблиц
python scripts/query_duckdb.py

# Список таблиц и схема одной таблицы
python scripts/query_duckdb.py --tables
python scripts/query_duckdb.py --schema fact_booking

# Отдельный запрос или все запросы SQL-файла
python scripts/query_duckdb.py --sql "SELECT * FROM dim_hotel"
python scripts/query_duckdb.py --file sql/analytics.sql 

## Проверки

Загрузчик выполняет SQL и выводит/сохраняет фактическое и ожидаемое значение
каждой проверки: число фактов в целом и по файлам, размеры справочников с учётом
неизвестных значений, пустые ключи, отсутствующие ссылки, соответствие типов
номеров отелю, дубли booking_id, сохранение пропусков детей.
Также проверяются обязательные значения, неотрицательные сроки до заезда, ночи
и число гостей, допустимые статусы и даты начиная с 2000 года. `children` может
быть NULL (4 строки в исходнике). `adr` не используется как сумма выручки и
не ограничивается снизу: в исходном H1 есть одна строка с `adr = -6.38`.

Проверки обработки ошибок на временных файлах и базе:

```powershell
python -m unittest discover -s tests -v
```

## Загрузка в ClickHouse

Нужны запущенный Docker Desktop и готовая `data/booking.duckdb` из раздела
«Запуск». Дополнительные Python-пакеты сверх `requirements.txt` не нужны:
загрузчик использует DuckDB и HTTP через стандартную библиотеку Python.
Из корня проекта:

```powershell
docker compose up -d clickhouse
docker compose ps
Invoke-RestMethod http://localhost:8123/ping
python etl/load_clickhouse.py
```

После ответа `Ok.` от `/ping` можно запускать загрузчик. Он создаёт отдельную
базу `booking_dw`, применяет `sql/ddl_clickhouse.sql` и переносит пять
справочников и `fact_booking` из DuckDB.

### Почему такой ORDER BY

В `fact_booking` выбран `ORDER BY (arrival_date_id, hotel_id, booking_id)`:
первый бизнес-вопрос рассматривает состоявшиеся бронирования по месяцам заезда
и отелям. Дата стоит первой, чтобы при прямом фильтре по диапазону
`arrival_date_id` сервер мог пропускать ненужные блоки данных; внутри даты строки
упорядочены по отелю. `booking_id` задаёт порядок внутри сочетания даты и отеля,
но `ORDER BY` не обеспечивает уникальность строк. Для небольших справочников
достаточно порядка по их идентификаторам.

### Повторная загрузка и сверка

Каждый запуск делает полный refresh: сначала `TRUNCATE` всех шести таблиц
витрины в целевой базе, затем загрузка из DuckDB.

После загрузки скрипт сравнивает количество строк каждой таблицы и результат
`sql/canonical_metric.sql` с DuckDB. Главная метрика — количество состоявшихся
бронирований (`Check-Out`), поэтому дополнительно сверяется сумма индикаторов
`CASE WHEN reservation_status = 'Check-Out' THEN 1 ELSE 0 END`

Результаты двух последовательных запусков сохранены в `etl/lab07_runs.txt`
