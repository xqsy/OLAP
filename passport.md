# Паспорт витрины

ФИО: Пашко Иван Антонович, Сакович Евгений Сергеевич · Дата: 16.10.2026 · Домен: D5 — бронирования.

## 1. Бизнес-цель витрины

Анализировать состоявшиеся бронирования двух отелей: сезонность по дате заезда и распределение по отелям, каналам, рыночным сегментам и странам гостей. Определять, какие источники дают больше состоявшихся бронирований.

## 2. Grain

Одна строка факта = одно бронирование в одном отеле, представленное отдельной строкой исходного CSV.

## 3. Fact-таблица

Источники: data/H1.csv — курортный отель, data/H2.csv — городской отель. 

| Имя | Grain | Примечание |
|-----|-------|------------|
| fact_booking | Одно бронирование | booking_id; внешние ключи hotel_id, arrival_date_id, status_date_id, country_id, channel_id, reserved_room_type_id, assigned_room_type_id; reservation_status, is_canceled, lead_time, stays_in_weekend_nights, stays_in_week_nights, adults, children, babies, adr; происхождение source_file, source_row_number |

Загружаем все статусы; главная метрика учитывает только Check-Out. hotel_id ссылается на единственную строку отеля; истории версий справочника нет.

В источнике нет ID бронирования. Технический booking_id формируем из кода H1/H2 и номера записи данных (с 1, без заголовка). Он идентифицирует запись фиксированного исходника, а не одно бронирование в разных выгрузках. Повторная загрузка того же сырья не должна увеличивать число фактов. Совпадение всех значений не является основанием удалять строку: это могут быть разные бронирования.

## 4. Меры

| Мера | Тип (sum ok / нет) | Определение |
|------|--------------------|-------------|
| Количество бронирований | Да | COUNT(*), включая отмены и незаезды. |
| Количество состоявшихся бронирований | Да | Главная метрика: количество строк с reservation_status = 'Check-Out'. |
| Количество отменённых бронирований | Да | SUM(is_canceled); поле 0/1 из IsCanceled. |
| Количество ночей | Да | stays_in_weekend_nights + stays_in_week_nights; для состоявшихся проживаний применяем фильтр Check-Out. |
| Количество гостей в бронировании | Да, с оговоркой | adults + children + babies; сумма не равна числу уникальных людей. Пропуски не подменяем нулями без основания. |
| Средний срок до заезда | Нет | AVG(lead_time); при объединении групп пересчитываем по сумме и числу непустых значений. |
| adr | Нет | Средняя дневная цена из ADR; сумма цен не является выручкой. |
| Доля отмен | Нет | Дополнительная метрика: 100.0 * SUM(is_canceled) / NULLIF(COUNT(*), 0); проценты не складываем. |

Главная метрика измеряется в бронированиях, а не в гостях, номерах или ночах. Условие is_canceled = 0 не заменяет отбор по Check-Out: незаезды не являются состоявшимися бронированиями.

## 5. Измерения

| Dim | Ключ | Важные атрибуты | SCD1 / SCD2 / нет |
|-----|------|-----------------|-------------------|
| dim_date | date_id, YYYYMMDD | full_date, year, quarter, month, day_of_week; даты заезда и последнего статуса | Нет: календарные признаки фиксированы. |
| dim_hotel | hotel_id — постоянный ключ отеля | hotel_code H1/H2, hotel_type | SCD1: одна строка на отель, атрибуты без истории. Тип определяем по файлу: H1 — Resort Hotel, H2 — City Hotel. |
| dim_country | country_id | country_code из Country; отдельное значение для неизвестной страны | SCD1 для исправлений без истории; новый реальный код — отдельная строка. Названий стран в текущей модели нет. |
| dim_channel | channel_id | Уникальная пара market_segment + distribution_channel из MarketSegment и DistributionChannel | SCD1 для исправлений без истории; новое реальное сочетание — отдельная строка. Сегмент не закреплён за каналом навсегда. |
| dim_room_type | room_type_id | hotel_id и room_type_code из ReservedRoomType / AssignedRoomType | SCD1 для исправлений без истории; новая пара «отель + код типа» — отдельная строка. Описаний категорий в текущей модели нет. |

Одна таблица фактов и пять измерений. Календарь используем в двух ролях: arrival_date_id — предполагаемый заезд; status_date_id — дата последнего статуса из ReservationStatusDate, не дата создания бронирования. Справочник типов номеров тоже используем дважды: забронированный и назначенный тип. Это не создаёт дополнительных таблиц.

Расшифровки типов номеров нет; одинаковые коды разных отелей не считаем одинаковой категорией. Обе ссылки на тип номера должны соответствовать отелю бронирования.

При загрузке обрезаем пробелы вокруг строк, текстовый NULL распознаём как пропуск. Для неизвестных значений измерений предусматриваем явные строки справочников. Дату заезда собираем из ArrivalDateYear, ArrivalDateMonth, ArrivalDateDayOfMonth.

**Решение по истории (З06, вариант B):** от SCD2 отказываемся. Для некалендарных справочников принимаем SCD1: исправления и изменения описательных атрибутов не сохраняют прежних значений. Старые бронирования отображаются с актуальными атрибутами справочников. Новые реальные коды и сочетания добавляем отдельными строками; исправление опечатки не считаем новой сущностью. Если правильное значение уже существует, ссылки переводим на него без создания дубля. dim_date содержит фиксированные календарные признаки; ошибки их вычисления исправляем.

Бронирование связываем с отелем напрямую через hotel_id, без выбора версии по дате. Обе ссылки на тип номера должны соответствовать этому hotel_id. Фактическая смена канала или назначенного типа номера у отдельного бронирования меняет его ссылку в факте, а не общую строку справочника.

H1/H2 не содержат журнала изменений атрибутов справочников. Текущий загрузчик полностью пересоздаёт витрину из фиксированных CSV, отдельной инкрементальной процедуры UPDATE/MERGE нет; ручные исправления в базе при перезагрузке не сохраняются. Тип отеля из файла применяем ко всему периоду. Цена отказа: при перезаписи hotel_type старые бронирования получат новый тип в отчётах, а распределение по типам за прошлые периоды может измениться. Три текущих бизнес-вопроса не группируют по типу отеля. Прежнюю классификацию после исправлений без истории восстановить нельзя; границы описаны в cut.md.

## 6. Три бизнес-вопроса

1. Как меняется количество состоявшихся бронирований по месяцам заезда в каждом отеле?
2. Какие каналы и рыночные сегменты дают больше состоявшихся бронирований?
3. Из каких стран приезжает больше гостей — по количеству состоявшихся бронирований, а не по числу людей?

## 7. Эталонный SQL одной метрики

**Главная метрика: количество состоявшихся бронирований за весь доступный период.**

Эталонный запрос сохранён в `sql/canonical_metric.sql`:

```sql
SELECT COUNT(*) AS completed_booking_count
FROM fact_booking
WHERE reservation_status = 'Check-Out';
```

Период отчётов выбираем по arrival_date_id. При отсутствии подходящих строк результат — 0.

## 8. Риски / cut

Набор охватывает бронирования с предполагаемыми заездами с июля 2015 по август 2017; крайние годы неполные. Сравниваем одинаковые периоды. 

Исходник отражает конечное состояние бронирования, а не историю изменений. Нет устойчивого ID гостя, числа доступных номеров и платёжного журнала.
