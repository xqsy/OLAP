# З04. Аналитический SQL

**Практика:** [[P04_аналитический_sql|P04]]  
**Вход:** таблицы из [[З03_витрина_duckdb|З03]] и три вопроса из [[З02_паспорт_star|паспорта]]

---

## Зачем

Показать, что по вашим таблицам можно **ответить на вопросы бизнеса обычным SQL** — ещё до дашборда.

Заодно закрепите **главную метрику**: один эталонный SQL-файл. Позже число из него должно совпасть с карточкой на дашборде ([[З11_сверка_sql_bi|З11]]).

## Что сделать

1. Минимум три аналитических запроса — по числу вопросов в паспорте.
2. Хотя бы в одном — оконная функция (доля или рейтинг).
3. Эталон главной метрики — отдельный файл и тот же текст в паспорте.

---

## Ход работы

### 1. Три ответа на три вопроса

Для каждого вопроса — свой `SELECT` в `sql/analytics.sql`.  
Рядом коротко: «вопрос 2 → этот запрос».

| Тип вопроса | Что обычно в SQL |
|-------------|------------------|
| «только Минск / только январь» | условие `WHERE` |
| «свернуть до региона / месяца» | `GROUP BY` |
| «топ-5» | сортировка и `LIMIT`, иногда нумерация |

### 2. Оконная функция

Обычный `GROUP BY` схлопывает строки в итог.  
Окно считает рядом со строками: долю категории в обороте дня или место магазина в рейтинге (`SUM() OVER (…)`, `RANK()`).

> [!tip]
> Нужен просто итог — `GROUP BY`. Нужна доля или «которое место» — окно. Не сдавайте одно вместо другого.

### 3. Эталон главной метрики

1. Возьмите одно главное число из паспорта (оборот, число закрытых обращений).
2. Положите расчёт в `sql/canonical_metric.sql` — один понятный скрипт.
3. Скопируйте SQL в паспорт как есть.
4. Прогоните и запомните число — пригодится при сверке с дашбордом.

Если определение метрики плывёт — поправьте паспорт на этом шаге, не на защите.

### 4. Чего не делать

`SELECT * FROM fact` — это не ответ бизнесу.  
Формула метрики не должна жить только в голове или в подписи будущего графика.
